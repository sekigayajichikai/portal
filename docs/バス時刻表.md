# 公式LINEのバス時刻表

「バス」→ 保存した1件目の行き方の時刻表（未保存なら方向選び）。「マイバス」→ 保存した行き方の一覧（最大3つ）。「バス検索」→ 方向選び。

## 仕組み（2026-10-12〜）

**いまの状態（2026-10-12）**: LINE の Webhook URL は line-webhook、BUS_EDGE_MODE は live（全員）。各人のバス設定はシートから一度だけ写した（46人・55件）ので、以後は Supabase が元。

```
住民のLINE → LINE → Webhook URL = Supabase Edge Function line-webhook
                       ├ 署名（X-Line-Signature）を確かめ、偽物は 401
                       ├ バス → ここで答える（Supabase のテーブルを読む）
                       └ それ以外（お問い合わせ・登録の返信・友だち追加・ブロック検知）→ 名簿GAS へそのまま転送
```

- コード: `supabase/functions/line-webhook/`（`index.ts` が受け口、`bus.ts` が時刻表のメッセージ作り）。
  デプロイ: `supabase functions deploy line-webhook --project-ref iplcopuwwzbtwoakqifh --no-verify-jwt`
- テーブル: `sql/migrations/2026-10-11-line-bus.sql`（時刻表・特別ダイヤ・祝日・各人の設定・名前変更待ち。画面からは読めない）。
- **元のデータはシートのまま**（名簿GAS の `BUS_SHEET_ID`）。名簿GAS の `syncBusToSupabase`（`BusSupabaseSync.js`）が毎日4時台に写す。
  時刻表や特別ダイヤのシートを直したら、手で `syncBusToSupabase` を実行するとすぐ反映（Edge Function の中の覚えは最大10分）。
- 各人のバス設定は、全員に切り替えるときに `importBusSettingsToSupabase` で一度だけシートから写し、以後は Supabase が元。
- **利用登録フォームの「いつも使うバス停」（2026-10-29）**: フォーム（liff-registration）で選んだ停留所を名簿GAS（`BusSupabaseSync.js` の `saveFormBusStop_`）が `POST ?op=user_setting` で送り、その人の設定の先頭（「バス」で最初に出るもの）に「いつものバス停」という名前で入れる。同じ行き方が別の名前で入っていれば先頭へ寄せる。マイページ表示用に `{ userId, read: true }` で先頭の設定を読める。
- 名簿GAS にもバスの処理（`BusTimetable.js`）は残っている。受け口のバスの処理が失敗したときは GAS に回すので、その予備になる。
  表示を変えるときは **両方を同じに直し**、`TZ=Asia/Tokyo node scripts/line-webhook-test/parity.mjs` で同じ出力になるかを確かめる。
- 受け口の試験: `WEBHOOK_TEST_SECRET=… node scripts/line-webhook-test/send.mjs バス "postback:bus_dir=往路"`
  （試験用の署名で送ると、LINE に返信せず、返すはずのメッセージを LINE の検証 API にかけて返す。`--forward` で GAS への転送も試す）。
- シークレット: `LINE_CHANNEL_SECRET`（LINE Developers の「チャネル基本設定」）／`LINE_CHANNEL_ACCESS_TOKEN`／`GAS_WEBHOOK_URL`（名簿GAS の Webhook URL）／
  `BUS_SYNC_SECRET`（名簿GAS と共通）／`BUS_EDGE_MODE`／`BUS_TEST_USER_IDS`（任意）／`WEBHOOK_TEST_SECRET`（試験用）。

### 段階的な切り替え（`BUS_EDGE_MODE`）
| 値 | バスを受け口で答える相手 |
|---|---|
| `off` | 誰もいない（全部 GAS へ転送するだけ） |
| `test` | `BUS_TEST_USER_IDS`（なければ `LINE_TEST_USER_ID`）の人だけ。ほかの人は GAS が答える |
| `live` | 全員 |

### 元に戻すとき
LINE Developers →「Messaging API設定」→ Webhook URL を名簿GAS の URL（`GAS_WEBHOOK_URL` と同じ）に書き戻す。次のメッセージから GAS が直接受ける。
ただし `live` にしたあとは、各人のバス設定の元が Supabase になっているので、GAS に戻すとシートの古い設定が使われる。

- 元は「バス時刻表」シート。停留所: 往路 野村住宅センター・西小学校前・中学校前・夏山坂上（→ 金沢文庫駅西口）、復路 金沢文庫駅西口・夏山坂上・中学校前・西小学校前（→ 野村住宅センター）、関ヶ谷（平日最終便だけ）。
- 正解は京急バスの公式時刻表（NAVITIME の発着時刻表 `transfer-cloud.navitime.biz/keikyubus/trips/section-timetables`）。
  **名簿GAS から直接読むと 403 で断られる**ので、Edge Function `line-webhook` の `op=navitime` が代わりに読む（2026-10-12 に判明。
  それまでの毎週の自動チェックは読めないまま「変更なし」を送っていて、土休日の 21:44 の便（実際は走っていない）に気づけなかった）。
  NAVITIME は**日本国外からの読み込みも 403 で断る**。GAS（米国）から呼ぶと Edge Function も米国の場所で動いてしまうので、
  GAS はヘッダー `x-region: ap-northeast-1` を付けて東京で動かす。
- 名簿GAS（`BusImportTimetable.js`）:
  - `refreshBusTimetableFromNavitime` … 公式と違う行の時刻だけを公式に合わせて直し、Supabase へ写す。
  - `addNatsuyamaSakaue` … 夏山坂上（バス停ID 00020374。中学校前の隣）の4行を公式から作って入れる（2026-10-12 追加。隣の自治会向け）。
    **まだ公開しない**ので、停留所選びには出さない（名簿GAS の `BUS_HIDDEN_STOPS` と bus.ts の `BUS_HIDDEN_STOPS`。公開するときは両方から消す）。
  - バス停ID は `NAVITIME_STOP_IDS`、比べる組み合わせは `NAVITIME_ROWS`。バス停を足すときはこの2つに足す。
- 毎週月曜の自動チェック（`BusScheduleChecker.js` の `checkBusScheduleChanges`）は、`NAVITIME_ROWS` 全部を平日・土休日とも公式と比べ、違えばメールで知らせる。

## 平日／土休日の判定

特別ダイヤシート → 土日 → 祝日 の順で決める。

- **祝日の正解は内閣府の「国民の祝日」一覧**（https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv 、振替休日は「休日」として入っている）。
  - 以前は Google の日本の祝日カレンダーを使っていたが、節分・雛祭り・七夕・七五三・クリスマス・大晦日・銀行休業日・母の日なども入っていて、
    **平日のクリスマス（2026-12-25 金）や節分などを土休日ダイヤにしていた**。説明欄でも見分けられなかった（2026-10-11 に確認。全部同じ扱い）。
  - 内閣府の一覧が読めないときだけ Google カレンダーで代用し、祝日でない行事は名前で除く。
  - 内閣府は毎年2月ごろに翌年分を載せる。一覧の最後の祝日が60日先より手前になったら、毎日の同期で担当者にメールする。
- **年末年始・夏休みなどバス会社が決めるダイヤは祝日ではない**ので、「特別ダイヤ」シートに人が書く（例: 12/31〜1/3 を土休日）。

## 表示の決まり（2026-10-12）

- 「◯◯ダイヤを見る」で今日と違うダイヤを見ているときは、見出しに今日の日付を出さない（「【平日ダイヤ】10月11日（日）」は事実と違うため）。
  本文に「次は 10月13日（火）」と、そのダイヤで次に走る日を出す（祝日・特別ダイヤも考えて60日先まで探す）。
- 今日のダイヤに戻したときは、切り替えではなくふつうの表示（日付と次のバス）にする。
- 0時〜4時台は見出しの日付に「今朝」をつけ、その日のバスがまだ出ていなければ「次のバス」を「始発」にする
  （寝る前に「明日の朝」を調べる人が日付を取り違えないように）。
- 待ち時間は1時間以上なら「あと 1時間15分」「あと 6時間」の形（「あと 392分」は読みにくいため）。

## 速さ

基準と測り方は `問い合わせ.md` の「速さ」と同じ（2秒以内は合格／2〜3秒は要注意／3秒超は遅すぎ）。

### 名簿GAS のまま縮めた（2026-10-11）
偽の返信トークンで測るため、返信失敗→エラー文の送信が1回多く、実際より 0.3〜0.5秒ほど長めに出る。

| 手順 | 対策前 | 対策後（温まった状態） |
|---|---|---|
| 何もしない文（GAS の起動待ちだけ） | 1.2〜2.0秒 | 1.0〜1.3秒 |
| 「バス」（保存した行き方の時刻表） | **3.7〜6.6秒** | 2.0〜2.2秒 |
| 「マイバス」（一覧） | 2.3〜3.7秒 | 1.6〜2.1秒 |
| ダイヤ切替 | 2.2〜3.5秒 | 2.0〜2.7秒 |
| 停留所を選ぶ → 時刻表 | 2.4〜2.8秒 | 2.3〜3.2秒（シートを開かない手順と差がなく、通信のばらつき） |

遅かった理由と対策:
- 各人のバス設定を毎回シートから読んでいた → 人ごとに6時間キャッシュ（保存・削除・名前変更で消す）。
- 祝日かを毎回 Google カレンダーに聞いていた（今日と明日の2回）→ 日付ごとに6時間キャッシュ。
- キャッシュがなくシート・カレンダーを開く遅いときだけ「読み込み中（…）」を出す（`busStartLoadingIfSlow_`）。

残りの約1秒は GAS の起動待ちで、GAS のままでは消せない。

### Supabase Edge Function に移した（2026-10-11〜12）
受け口の中の処理時間（試験用の署名で測定。LINE への返信の通信は含まない）。

| 手順 | Edge Function | （参考）GAS |
|---|---|---|
| 「バス」（起動直後の1回目） | 1.2秒 | 3.7〜6.6秒 |
| 「バス」（2回目以降） | 0.4秒 | 約2秒 |
| 方向・停留所を選ぶ／ダイヤ切替 | 0.3〜0.4秒 | 2〜3秒 |
| 保存・名前変更・削除・マイバス | 0.1〜0.7秒 | 2〜3秒 |

時間のほとんどは DB への問い合わせ（1回 約0.1〜0.3秒。DB はシンガポール）。2026-10-12 に実機で「めちゃ早くなった」ことを確認。
バス以外は受け口 → GAS の順になるので、GAS だけのときより少し（受け口の分）遅れる。

## 管理画面「バス」タブ（設計・未実装。2026-10-12 の案）

いまGASのエディタで関数を実行している作業や、コードを書き換えている作業を、ポータルの管理画面に置き換える。
タブは既存の「回覧板・レポート・週次配信・リッチメニュー・予定・マスタ」に「バス」を足す。

### 最初に作るもの（いま手間がかかっている作業の置き換え）
1. **時刻表を見る**: 停留所 × 方面 × 平日・土休日の時刻を一覧で確認。最後に公式と突き合わせた日時と結果も出す。
2. **公式の時刻表に合わせる**: 「公式と比べる」で違いを表で出す（例: 21:44 がこちらにだけある）→ 確かめてから「公式に合わせる」。
   GAS の `refreshBusTimetableFromNavitime` の代わり。
3. **特別ダイヤ**: 年末年始・夏休みなどの期間（開始日・終了日・平日／土休日・メモ）を画面で足す・消す。シートを開かなくて済む。
   12月に入ったら「年末年始のダイヤは入れましたか？」と出す。
4. **停留所の公開・非公開**: 夏山坂上のような準備中のバス停をスイッチで出し入れ（いまはコードの `BUS_HIDDEN_STOPS` を書き換えている）。

### 次に作るもの
5. **使われ方**: バス設定を保存している人数、停留所ごとの保存数、よく見られる時間帯（事業化の構想の「地域交通の利用データ」の土台）。
6. **祝日の確認**: 内閣府の一覧から取り込んだ祝日と、来年分が載っているか。

### 作り方の方針
- **時刻表・特別ダイヤの元を Supabase に移す**。画面で直したものが毎日4時の同期（シート → Supabase）で上書きされないように。
  シートは必要なら書き出し用に残す。GAS のバスの処理（いまは受け口が失敗したときの予備）は、Supabase から読むか、予備をやめるかを決める。
- **最初から「どの自治会のものか」を持たせる**（`docs/事業化の構想.md` の保守コスト①③⑥⑦）。画面は当面 関ヶ谷だけ。
  時刻表は路線ごとに共通、各人の設定・使うバス停・行き先の名前・外すバス停は自治会ごと。
- 画面はほかのタブと同じログインで使う。公式の時刻表を読む・直す操作は Edge Function を通す（GAS からは NAVITIME を読めないため）。

### 決めること（作り始める前に）
1. 最初に作る範囲は 1〜4 でよいか
2. 時刻表・特別ダイヤの元をシートから Supabase に移し、シートは使わない方向でよいか
3. Supabase に一本化したら、GAS のバスの処理（予備）を消してよいか
