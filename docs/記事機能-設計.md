## 命名（確定）

| 層 | 名前 | 用途 | コード識別子 |
|---|---|---|---|
| コーナー名（器） | **関ヶ谷レポート** | 記事をぶら下げる連載枠（newsletter 1件） | `sekigaya-report` |

将来、器「関ヶ谷レポート」にイベント以外（お知らせ／活動紹介／インタビュー等）のカテゴリを足して拡張できる。

## 基本方針：既存 `articles` 基盤に乗せる

circulars は Vite + React の SPA。回覧板は `newsletters`（月号）＋ ぶら下がる `articles`（記事）構造。
`articles` は既に `content`(Markdown/ReactMarkdown対応)・`event_date/time/location`・複数写真・`thumbnail_url`・`image_display='tall'`・`visibility`・`tags`・`is_pinned` を持ち、イベントレポートにほぼそのまま使える。

**採用案（案B）**: 「関ヶ谷レポート」という常設 newsletter を1件作り、記事をそこにぶら下げる。
- 理由: 公開ビュー・記事表示・承認フローがすべて newsletter 前提で動くため、それを壊さず最小改修で乗る。
- 却下案A（`newsletter_id` 任意化）= 公開ビューのクエリ全面見直しでリスク大。却下案C（別テーブル）= 編集UI・表示の二重化。

## リスク・宿題（MVPを止めないが並行で対応）

1. **`visibility` フィルタ導入は本番の見え方を変える**。既存記事は `visibility` デフォルト `members-only`、現状フィルタ無しで全記事が公開ビューに出ている。フィルタを入れると既存 members-only 記事が非ログインで消える → 導入時は既存記事の visibility を実データで確認してから慎重に。
2. **RLS 未使用・公開ガードはUIのみ**。DBを直接叩けば未承認でも公開可能な状態。一般公開まで広げるなら堅牢化（RLS or サーバ側チェック）を別途検討。
3. SQL は Supabase SQL Editor で手動実行（本番は `sekigaya-portal` = `iplcopuwwzbtwoakqifh`。旧プロジェクト `ubxkjjyxzuvevbdwrpct` は 2026-09-05 に移行完了し未使用）。
