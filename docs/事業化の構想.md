# 事業化の構想（複数自治会への展開）

2026-10-12 の相談の記録（同じ日に `/btw` で聞いたメモも合わせた）。
きっかけ: 隣の**夏山自治会**から「バス時刻表をうちにも入れたい」と言われた。
関ヶ谷自治会と夏山自治会は仲が良く、将来は裏方の運営（バックオフィス）をまとめる案も出ている。
こういうきっかけをつかみつつ、**ビジネスの種として広げたい**。そのためには、**複数の自治会で使っても管理・保守の手間を最小にする**ことが前提になる。

---

## 質問

1. このきっかけがビジネスの種になる可能性・展開を最低5つ。バス時刻表にとらわれず、ビジネスの範囲をとらえてほしい。
2. NAVITIME などはバス時刻表をすぐ出せそうだが、公式LINEアカウントに入れるのは別のビジネスになりうるか。
3. 複数の自治会で実装して、自分の管理・保守コストを最小にする案を最低5つ。

---

## 1. ビジネスの種になる可能性

売っているのは「バス時刻表」ではなく、**住民がもう友だち登録している公式LINEを、地域の窓口として動かす仕組み**。
バスはその窓口を毎日開いてもらう理由（入口）になる。

### ① 自治会向け「公式LINE運用パッケージ」（月額のサービス）
- 中身: 名簿登録・回覧板・週次のお知らせ配信・お問い合わせ受付・リッチメニューの出し分け・バス時刻表・ごみの日など、今あるものをまとめて提供する。
- 相手: 公式LINEを作ったが運用できていない自治会や、これから作る自治会。
- 強み: 役員が毎年替わっても回る（仕組みが覚えていて、人に頼らない）。導入した自治会どうしで改善を分け合える。

### ② 自治会の裏方業務の共同化（事務局代行・BPO）
- 中身: 名簿の管理、会費の集金・記録、回覧板づくり、問い合わせの一次対応、配信作業などを、複数の自治会からまとめて引き受ける。今回話に出ている「バック業務をまとめる」案そのもの。
- 強み: 仕組み（①）を使えば1人で何自治会も回せる。AI で回覧板の記事化・予定の抽出はもうできている。
- 形: 自治会から業務委託費を受け取る。①を使う権利は込みにする。

### ③ 行政・連合町内会・区役所向けの「地域への配信の道」
- 中身: 区や連合町内会からのお知らせ（防災・イベント・制度）を、各自治会の公式LINEにまとめて届ける。どれだけ読まれたかも返す。
- 価値: 行政は「回覧板が届かない・読まれない」ことに困っている。自治会ごとの公式LINEを束ねれば、確実に届く道になる。
- 形: 区の委託事業、地域活動・DX の補助金。

### ④ 防災・見守り（安否確認・要支援者の把握）
- 中身: 災害時の安否確認（「無事です」ボタン）、避難所の情報、要支援者名簿の更新の声かけ、防災訓練の出欠など。
- 価値: 自治会にとってほぼ義務で、行政の補助の対象にもなりやすい。名簿と LINE がつながっていることが強み。

### ⑤ 地域交通の利用データ・地域交通の相談（交通事業者・自治体向け）
- 中身: どのバス停の時刻表が、いつ・何人に見られているかの集計（個人が特定できない形）。
  コミュニティバスやデマンド交通の需要把握、ダイヤ改正の住民への周知の代行にも使える。
- 価値: 交通事業者や区は「実際に誰が乗りたいか」のデータを持っていない。
- 注意: 集計だけを渡し、名簿の情報とは結びつけない（規約と住民への説明が必要）。

### ⑥ 地域の店・事業者の告知枠（地域メディア）
- 中身: 回覧板・週次のお知らせ・関ヶ谷レポートに、地域の店・教室・医院のお知らせ枠を設ける。
- 価値: 地域の住民だけに確実に届く広告は少ない。自治会の収入にもなり、導入の後押しになる。
- 注意: 自治会の中立性。載せる基準を決めておく。

### ⑦ 似た団体への横展開
- 相手: マンションの管理組合、PTA・子ども会、商店会、老人会、地域のスポーツ団体。
- どれも「名簿・連絡・出欠・会費・問い合わせ」という同じ悩みを持っていて、①の機能をほぼそのまま使える。

### ⑧ 導入支援・研修（デジタル化の伴走）
- 中身: 公式LINEの開設、リッチメニューづくり、役員向けの使い方講座、高齢の住民向けの登録会。
- 形: 1回いくらの導入費。区の「デジタル支援」の委託として受けられることもある。

## 2. NAVITIME などがあるのに、公式LINEに入れる意味はあるか

**ある。別のビジネスになりうる。** NAVITIME やジョルダンは「誰でも・どこでも」の**検索**で、こちらは「この地域の人の**窓口**」。

| | 乗換案内（NAVITIME など） | 自治会の公式LINE |
|---|---|---|
| 開くきっかけ | 自分で調べるとき | 毎日のお知らせ・回覧板と同じ場所。メニューのボタン1つ |
| 中身 | 全国のすべてのバス停 | 地域で使うバス停だけ。保存した「行き」「帰り」がすぐ出る |
| 地域の事情 | 載らない | 自治会が補足できる（運休・工事・お祭りの迂回・特別ダイヤ） |
| 誰が使っているか | わからない | 名簿とつながる（地域ごとの利用、高齢の方への配慮） |
| ほかの機能 | なし | 回覧板・問い合わせ・防災・ごみの日とまとめて使える |

バス時刻表だけで勝負すると乗換案内に勝てない。**「地域の窓口」の中の1機能**として価値が出る。

**注意（事業にするなら必ず）**: いまは京急バスの公式時刻表（NAVITIME のページ）を読み取って使っている。
自分の自治会で使う分にはともかく、**お金をもらって他の自治会にも出すなら、データの出どころと利用条件を確かめる**必要がある。
- 候補: 交通事業者が公開している標準的な時刻表データ（GTFS-JP。公共交通オープンデータセンターなど）。京急バスが公開しているか、利用条件はどうかを確認する。
- 公開されていなければ、京急バスや区に「住民向けの案内に使いたい」と相談する。地域の利用データ（⑤）を返す形にすれば、協力が得やすい。

## 3. 複数の自治会に入れても、管理・保守コストを最小にする案

### ① 1つの仕組みを全部の自治会で使う（マルチテナント）
- 自治会ごとにコピーを作らない。Edge Function は1本、データベースも1つにする。行ごとに「どの自治会のものか」（`organization_id`）を持たせる。
- LINE の Webhook は、公式LINEアカウントごとに URL を分けるか、届いた通知の `destination`（どのアカウント宛か）で見分ける。
- 直す・足すのは1か所だけで、全部の自治会に同時に届く。自治会が増えても、デプロイするのは1つだけで済む。

### ② GAS をやめて Supabase に集める
- GAS は自治会ごとにスプレッドシートとコードのコピーができやすい。コピーが増えるほど、直す場所も増える。
- 名簿・お問い合わせ・バス設定を Supabase に移す（バスは移行済み）。
- スプレッドシートは「見る・書き出す」用途だけにする（必要なら毎日写す）。

### ③ 自治会ごとの違いは「設定」にして、管理画面で各自治会が自分で変える
- 違う点は、自治会の名前、公式LINEの鍵、使うバス停、問い合わせの種類と担当者のメール、リッチメニュー、使う機能の ON/OFF など。
- これらはコードではなく設定の表に持たせ、ポータルの管理画面で各自治会の担当者が変えられるようにする。
- 自分がやるのは「新しい自治会を1行足す」だけにする。
- **いまコードに直接書いてあるもの**も設定に出す: 行き先の名前（「金沢文庫駅 行き」「野村住宅センター 行き」）、停留所選びから外すバス停（関ヶ谷・終点・準備中の夏山坂上）、方面の色。
  これを「自治会の設定表」に移せば、夏山自治会を足すときもコードを変えずに済む。
- バス停の選択・色・案内文などを管理画面で変えられるようにして、「シートを直してください」と頼まれる仕事をなくす。

### ④ 作り込みをしない（標準パッケージ＋機能の ON/OFF）
- 自治会ごとの特注は受けない。要望は「全員に役立つなら標準機能として足す」「そうでなければ断る」の2択にする。
- 文言・メニュー・案内文はテンプレートを用意して、各自治会は選ぶだけにする。

### ⑤ データの更新と見張りを自動にする
- 時刻表は公式のデータから自動で更新する。違いが出たら自動で知らせる（今回作った毎週のチェックの形）。祝日も自動で更新する。
- Edge Function の失敗や、LINE の送信失敗は自動でメールや LINE に知らせる。住民より先に自分が気づけるようにする。
- 表示が変わっていないかの自動試験（今の `parity.mjs` や `send.mjs` の形）を、変更のたびに流す。
- **見張りは1つにまとめる**: エラーや同期の失敗は、全自治会の分を1通のメールにまとめて受け取る。1か所を直せば全員が直る形にしておけば、保守の手間は自治会の数にほぼ比例しない。

### ⑥ 時刻表・祝日・特別ダイヤは全自治会で共有する
- 京急バスの「路線・停留所・時刻」は、自治会ごとではなく**共通の1つの表**で持つ。各自治会は「うちが使うバス停と行き先」を選ぶだけにする。
  - 夏山坂上のように、隣の自治会のバス停でも同じ路線なら、表は1つで足りる。
- 時刻改正の取り込み（今の `BusImportTimetable` ／ `refreshBusTimetableFromNavitime`）と、改正の見張り（`BusScheduleChecker`）は、1回動かせば全自治会の分が済む。保守がいちばん楽になるところ。
- 祝日の表も全員で共通（内閣府の一覧から自動）。特別ダイヤ（年末年始など）は**路線ごとに1つ**持てば足りる。

### ⑦ 自治会ごとにデータを分ける（個人情報の説明責任）
- **LINE のユーザーIDは、公式アカウント（プロバイダー）ごとに別のもの**になる。同じ人でも、関ヶ谷の公式LINEと夏山の公式LINEでは別のIDになる。
  そのため、各人の設定や名簿は、必ず「どの自治会（どの公式アカウント）のものか」と組にして持つ。
- 名簿・バス設定・問い合わせなどの表には「どの自治会のデータか」の列を足す。ほかの自治会のデータが混ざらない・見えないようにする（行ごとの保護 RLS）。
- 「どの自治会の、誰が、何を見られるか」を住民に説明できる形にしておく。個人情報を預かる以上、説明責任の面で重要。

### ⑧ 問い合わせの一次対応は各自治会、自分は二次対応だけ
- 住民からの問い合わせは、各自治会の担当者が受ける（お問い合わせ機能の担当者の設定）。
- よくある質問は案内文・FAQ にして、LINE の中で自動で答える。
- 自分に来るのは「仕組みの不具合」だけにする。不具合の報告にも同じ問い合わせ機能を使う。

### ⑨ 新しい自治会の導入を手順書と自動化で「作業30分」にする
- 公式LINEの開設手順書（画面の写真つき）を用意する。
- 鍵を管理画面に貼るだけで、Webhook の設定・リッチメニュー・時刻表の取り込みまで自動で進むようにする。
- 最初の自治会（隣の自治会）で手順を作り、2つ目からはそれをなぞるだけにする。

### ⑩ 費用の形で保守を支える
- 保守は「月額いくら（自治会の規模で段階）」で受ける。無償で引き受けると、保守が自分の持ち出しになる。
- 共同事務局（事業②）を作るなら、日々の運用（配信・名簿の更新・問い合わせ）はそこで担当し、自分は仕組みの改善に集中する。
- 費用の目安:
  - Supabase と LINE（返信は無料、一斉送信は通数で費用）は、小さい自治会ならほぼ無料枠で収まる。
  - 自治会が増えたら、使った分を自治会ごとに按分する。

## 4. お金の取り方（マネタイズ）

前提: 自治会のお金は会費で、使い道は年1回の総会で決まる。役員は毎年替わり、ボランティアの感覚が強い。
**「いくら払えるか」より「何が浮くか・誰が払うか」**で考える。

### お金を払う人と取り方
| 取り方 | 払う人 | 目安の考え方 | 向き・不向き |
|---|---|---|---|
| A. 月額の利用料 | 各自治会 | 世帯数で段階。回覧板の印刷・配布の手間と費用が減る分より安く | 薄く広く。1自治会あたりは小さい |
| B. 導入費 | 各自治会 | 公式LINEの開設・名簿の移行・役員向け講座・住民の登録会をまとめて | 最初の1回。手間に見合う額に |
| C. 事務局代行（裏方業務の共同化） | 各自治会（数自治会で分担） | 名簿・会費・回覧板づくり・問い合わせ一次対応などを業務委託で | **いちばん大きい**。手間（人）がかかる分、仕組みで減らせるほど利益になる |
| D. 連合町内会・区とまとめて契約 | 連合町内会・区役所 | 地区まとめて導入、委託事業・補助金（制度名と条件は要確認） | 1回の契約で何自治会も入る。**売り込みの手間がいちばん少ない** |
| E. 地域の店の告知枠・協賛 | 地域の店・事業者 | 月いくらの掲載。自治会に一部を戻す | 自治会の負担を下げる補助の収入 |
| F. 交通事業者・区への協力 | 交通事業者・区 | 利用の集計・ダイヤ改正の周知の代行 | 先の話。データがたまってから |

### おすすめの順番
1. **夏山自治会は「一緒に作る相手」として、無料か安い試験価格**で始める。代わりに、使った感想・改善の協力・ほかの自治会への紹介をお願いする。
   ここで「導入の手順（30分）」と「何が浮いたか」（回覧板の印刷・配布・問い合わせ対応の時間など）の数字をそろえる。
2. その数字を持って、**連合町内会（地区）にまとめて提案**する（D）。自治会を1つずつ回るより、売り込みの手間が圧倒的に少ない。
3. 裏方業務の共同化（C）は、関ヶ谷・夏山の2つで形を作ってから値段を決める。収入の柱はここになりやすい。
4. A（月額）は保守の費用をまかなう土台。安く、ただし無料にはしない（無料だと保守が自分の持ち出しになる）。

### 費用のほう
- 仕組みを全自治会で1つにすれば（3 の①⑥）、自治会が1つ増えても費用はほぼ増えない（Supabase は有料プランでも月数千円程度から）。
- LINE の公式アカウントは各自治会のもので、一斉送信の料金はその自治会がLINEに払う（返信は無料）。
- 増えるのは**人の手間**（問い合わせ・導入・事務局代行）。だから「1自治会あたりの手間」を測って値段に反映する。

### 気をつけること
- 予算は総会で決まるので、提案は総会の前（年度の切り替わり前）に。
- 役員が替わっても続くよう、契約は「自治会」と結び、担当者が替わっても引き継げる形に。
- 「お金を取るなら中立か」と見られやすい。名簿などの個人情報は売らない・広告に使わないことを最初に約束する。
- 時刻表のデータを有料サービスで使う場合の利用条件（2 の注意）。

## 次の一歩（案）

1. **夏山自治会を「2つ目の自治会」として最初の導入例にする**:
   - 夏山自治会の公式LINEに同じ仕組みを入れる（マルチテナントの最初の試験）。
   - 夏山坂上の時刻表は準備済み（停留所選びにはまだ出していない）。
2. その前に、データの土台を「どの自治会のものか」で分けられる形にする（保守コストの①③⑥⑦）。
   - バスでいえば、時刻表は共通のまま、各人の設定と「使うバス停・行き先の名前」を自治会ごとにする。
3. 京急バスの時刻表データの利用条件を確認する（2 の注意）。
4. 裏方業務の共同化（事業②）の話し合いで、**どの業務を・いくらで**引き受けるかの叩き台を作る。
